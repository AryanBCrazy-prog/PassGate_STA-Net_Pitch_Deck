================================================================================
GATEPASS: HOW IT WAS BUILT, PROMPT BY PROMPT
================================================================================

GatePass is a low-cost entry-access system for residential housing societies.
It was built end to end through a series of prompts to an AI coding assistant.
This file records them in order, grouped by phase.

The method:
  1. Start with a full system brief (the problem, the actors, the hardware, the rules).
  2. Specify one interface in exact detail (every page, widget, flow and timer).
  3. Refine step by step: layout, visual identity, behaviour, then new features.
  4. Ship it.

Every refinement names the specific problem and the specific fix.


================================================================================
PHASE 0: SYSTEM CONTEXT (given first, before any build request)
================================================================================

Purpose: give the assistant the whole system design up front, so every later
decision is made in context. The assistant was told not to build any of this
yet, and not to reuse the brief's own terminology in the interface.

--------------------------------------------------------------------------------
0.1  The problem
--------------------------------------------------------------------------------
Entry-access tool for residential housing societies, built for a low-cost model.

Today, a delivery person, guest or anyone without standing permission can walk
in through the main entrance and is never monitored again. They can go to the
wrong house, steal, or damage private society property. This web application
aims to stop that.

--------------------------------------------------------------------------------
0.2  Interfaces
--------------------------------------------------------------------------------
  Interface X : for guards
  Interface Y : for residents
  Guests have no interface of their own.

--------------------------------------------------------------------------------
0.3  The sensor (core hardware concept)
--------------------------------------------------------------------------------
A small, cheap device that receives:
  - an OTP from visitors with one-time access,
  - a passkey from trusted regulars,
  - a password from household members.

It also handles small control signals:
  - ALIVE   : replies "alive" if the system works (it verifies a fake OTP in the
              background). Guards see this confirmed on their dashboard.
  - NO REPLY: if nothing comes back, guards get a dashboard warning.
  - STOP    : rejects an already-issued OTP when the guards withdraw it.

--------------------------------------------------------------------------------
0.4  People and what each can do
--------------------------------------------------------------------------------
  Household members     : listed by the household.
  Regulars              : daily approvals (maids, cooks), plus known or trusted
                          people (relatives, friends).
  Visitors              : approved in advance by a resident (known guests), or
                          arriving as services (unknown people) with a tie-in to
                          delivery apps (Swiggy, Zomato, Blinkit) that always get
                          access.
  Security runs on every category regardless.

--------------------------------------------------------------------------------
0.5  Access control and sensors
--------------------------------------------------------------------------------
  - Each sensor has a distinct code.
  - Household members and regulars get automatic entry by password or passkey.
    (Face entry is planned as a cheaper future option and is out of scope.)
  - Visitors enter an OTP at every sensor.
  - Sensors behave like bots: they receive alive / stop / no-reply messages from
    the guards and send yes / no back, which is translated into plain sentences
    on the guard dashboard.

--------------------------------------------------------------------------------
0.6  Visitors and guards
--------------------------------------------------------------------------------
  Visitors : request access at the gate or receive it from a resident, then
             enter their OTP at each access point.
  Guards   : accept requests from regulars; monitor the platform (review, sensor
             failure, view logs); revoke an OTP under the right conditions and
             remove unwanted people.


================================================================================
PHASE 1: FULL SPECIFICATION OF THE GUARD INTERFACE
================================================================================

Purpose: one detailed specification covering look, structure, every page, every
widget, every flow and every simulated event, so the first build is complete.

--------------------------------------------------------------------------------
1.1  Visual identity and chrome
--------------------------------------------------------------------------------
  - Minimal, aesthetic white and orange-ish theme. Font: Polaris.
  - Top bar, entirely white, with a Restart button and two view buttons:
    Laptop mode and Phone mode, each at the correct dimensions and orientation.

--------------------------------------------------------------------------------
1.2  The five pages
--------------------------------------------------------------------------------
  Page 1  Layout. A main gate with five buildings (wings A to E) inside.
          Six sensors in total: one at the main gate, one per building.
  Page 2  Who is entering? Five buttons:
            1) Delivery driver (Swiggy, Postal Service)
            2) Essential services (Fire fighters, Police)
            3) Unknown visitor wanting to enter
            4) A relative
            5) A blank button that does nothing
  Page 3  Phone number entry (a real number is entered).
  Page 4  Building (A to E), then floor (1 to 5), then house (1 to 8) with family
          last names shown. A search bar sits centred above, searchable by last
          name, with the face of the family head. Last names are randomly
          assigned to reflect India's demographics (religion, caste), with
          appropriate names.
          After confirming the house once, show "access granted" and send the
          OTP to the number collected on page 3.
  Page 5  Main dashboard with four widgets (laptop positions; stacked on phone):
          - Bottom left : sensor list with status (green = active, red = not
            active), a summary line naming inactive sensors, and a "check all
            sensors" button that pings each one and shows an active or no-reply
            message beside it.
          - Bottom right: every guest currently inside and the last checkpoint
            they passed, a red-flag button that revokes their OTP, and a
            three-dot control that opens their check-in log.
          - Top right   : "Sign in new guest" button (returns to page 2 and runs
            the same flow), with a "residents waiting approval" list below it.
          - Top left    : emergency messages (e.g. sensor down, intruder alert).

--------------------------------------------------------------------------------
1.3  Flows (every flow ends on page 5; messages show for 5 seconds)
--------------------------------------------------------------------------------
  1) Delivery driver : pages 2 to 4, ending with "Verified by Swiggy".
  2) Essential svcs  : skip everything, just "access granted".
  3) Unknown visitor : pages 2 to 4, ending with "waiting for resident
                       permission"; the name is added to the top-right widget.
  4) Relative        : pages 2 to 4, ending with "On resident list".
  5) Blank button    : continue to page 5, do nothing different.

--------------------------------------------------------------------------------
1.4  Simulated events, timed from arriving on page 5
--------------------------------------------------------------------------------
  1) Delivery   : a suspicious-activity indicator, beeping red, as the visitor
                  tries to enter two other wings (x and y, different from the
                  one chosen on page 4).
  2) Essential  : nothing.
  3) Unknown    : the name in the waiting list turns green with "access granted"
                  right in its box, then is removed.
  4) Relative   : the sensor for the chosen wing is shown as not working in the
                  sensor widget, with a message in the emergency section too.
  5) Blank      : nothing.


================================================================================
PHASE 2: VISUAL DIRECTION (three design iterations)
================================================================================

Purpose: take the first build from "works" to "looks designed". Each round
names exactly what is wrong, supplies a concrete reference, and sets a
measurable constraint.

--------------------------------------------------------------------------------
2.1  Round 1: formatting
--------------------------------------------------------------------------------
Fix the formatting and looks. It reads as a typical AI-generated website.

--------------------------------------------------------------------------------
2.2  Round 2: reference-driven identity (a pixel-art event site)
--------------------------------------------------------------------------------
  - Use the same layouts, colour theme, fonts, layouts and animations as the
    reference site.
  - On laptop, everything must fit on ONE screen: no scrolling on page 5.
  - Phone layout stays as it is.
  - Top left of the bar reads "GatePass".

--------------------------------------------------------------------------------
2.3  Round 3: second reference (an events platform, light theme)
--------------------------------------------------------------------------------
  - Drop the old style entirely; use the reference's formatting, fonts and
    colours, in a light theme.
  - No loading screen between page 4 and page 5.
  - Name field rules:
      * not shown for delivery driver or essential services,
      * compulsory for unknown visitor and relative,
      * optional for the blank button, without saying "optional" in the box.
  - Make the three summary boxes smaller, with smaller text, and make the
    emergency section larger.

--------------------------------------------------------------------------------
2.4  Round 4: polish and correctness
--------------------------------------------------------------------------------
  - A dynamic, good-looking background that suits the design, and does not look
    AI-generated.
  - A prettier, more modern font.
  - A bigger society image on page 1.
  - Emergency box: empty by default; when an alert arrives, flash red. Show
    several problems one below the other in a rectangle of fixed dimensions.
  - Layout bug: after an alert arrived, the widgets on the right disappeared.
    Fix this.


================================================================================
PHASE 3: FEATURE EXTENSIONS ON THE GUARD DASHBOARD
================================================================================

Purpose: make the "guests inside" widget carry the information a guard needs to
act, directly in the row.

  - Show each guest's phone number in the guests-inside section.
  - Show each guest's OTP next to their name, and save it for them.
  - Remove the mentions of "no SMS service connected" and call it an OTP, not a
    demo number.
  - Add a "Revoke OTP" button next to the suspicious-activity alert for the
    person concerned.


================================================================================
PHASE 4: SECOND INTERFACE (SAMPLE ENTRY) AND TIMING
================================================================================

Purpose: show the whole loop, from the guard issuing an OTP to a visitor using
it at a physical sensor.

--------------------------------------------------------------------------------
4.1  Structure
--------------------------------------------------------------------------------
Add a second tab to the top bar: tab 1 is the guard interface, tab 2 is a sample
entry. The guard interface is finished; the only change there is that every
10-second timer becomes 30 seconds.

--------------------------------------------------------------------------------
4.2  Sample entry, left side: the sensor
--------------------------------------------------------------------------------
  - Pick one of the guests already created.
  - Show a numeric pad and keyboard on a realistic-looking sensor.
  - An "Active" badge sits above it. If the sensor has been declared inactive
    (as in the relative simulation), show "Inactive" and do not accept numbers.
  - Two options at the bottom:
      1) Speak OTP: lets the person in automatically, in every case.
      2) Enter OTP: lets them in only if the OTP typed on the pad matches the
         one assigned to that person.

--------------------------------------------------------------------------------
4.3  Sample entry, right side: the gate
--------------------------------------------------------------------------------
A gate simulation, small and set in a lobby (not large):
  - Correct OTP: the gate opens and the person goes through.
  - Speak OTP: always opens.
  - Otherwise: entry is denied.


================================================================================
PHASE 5: SHIPPING
================================================================================

  - Put the project on an existing public GitHub repository (owned by a
    collaborator, so this meant working out access and the right route).
  - Host it as a website once it is on GitHub.
  - Document the build: this file.


================================================================================
SUMMARY OF APPROACH
================================================================================

  - Context before code: the full system design was given before anything was
    built.
  - Exact specification: pages, widgets, flows and timers defined in detail
    for the first build.
  - Specific feedback: each refinement states the exact problem and fix.
  - Concrete references: design direction came from real sites, not adjectives.
  - Hard constraints: "one screen on laptop, no scroll", "fixed dimensions",
    "no loading screen".
  - Iteration: layout first, then identity, then behaviour, then new features,
    then shipping.
